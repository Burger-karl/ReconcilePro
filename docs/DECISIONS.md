# Decisions

One entry per decision: what we chose, why, and what we rejected. Newest at the bottom.
If a decision changes, add a new entry that supersedes the old one; don't edit history.

---

## D-01 — Money is integer kobo
- **Decision:** every amount is stored and computed as an integer number of kobo (`BIGINT` in Postgres, `int` in Python,
  `number` in TypeScript). Columns end in `_kobo`. Naira formatting happens only in `frontend/lib/money.ts`.
- **Why:** floats cannot represent 0.1 exactly, so sums drift (`0.1 + 0.2 != 0.3`). Integers add exactly.
  ₦ amounts up to ~90 trillion naira fit in a BIGINT of kobo, far beyond any SME.
- **Rejected:** `NUMERIC`/`Decimal` — exact, but easy to mix with float by accident in Python and JSON, and it adds a type
  the author has to explain everywhere. One integer type is simpler.

## D-02 — VAT is 7.5% of the subtotal, rounded half up to the nearest kobo
- **Decision:** `vat_kobo = (subtotal_kobo * 75 + 500) // 1000`. `total_kobo = subtotal_kobo + vat_kobo`.
- **Why:** 7.5% is the current Nigerian VAT rate. Integer arithmetic keeps D-01; adding 500 before the floor division
  by 1000 is "round half up" (e.g. 10 kobo × 7.5% = 0.75 kobo → 1 kobo). Python's `round()` is banker's rounding, which
  would surprise an accountant, so it is not used.
- **Rejected:** VAT per line item — we have no line items (D-04).

## D-03 — Statement line fingerprint
- **Decision:** `fingerprint = sha256(workspace_id | source | value_date | amount_kobo | normalised narration | bank_reference | balance_kobo)`.
  Normalised narration = upper case, whitespace collapsed to single spaces, trimmed. If a bank format has no balance
  column, append the occurrence index of that identical line within the file (1st, 2nd …).
- **Why:** re-importing the same file (or an overlapping date range) must add nothing (invariant 2). With a running
  balance, two genuinely identical payments on the same day still differ by balance. Without one, the occurrence index
  keeps both lines while still making the second import of the same file a no-op.
- **Rejected:** fingerprinting the whole file — overlapping statements (1–15 Oct, then 1–31 Oct) would double count.

## D-04 — Invoices have no line items in the MVP
- **Decision:** an invoice stores `subtotal_kobo`, `vat_kobo`, `total_kobo` and a description, not a list of lines.
- **Why:** matching and allocation only need the total. Line items add a table, a form and tests without helping the
  hard part. Two-week budget.
- **Rejected:** `invoice_lines` table. Can be added later without changing allocations.

## D-05 — Invoice status is derived, in a fixed order
- **Decision:** only `draft`, `sent`, `void` are stored. Display status is computed in this order:
  void/draft (stored) → `paid` (outstanding = 0) → `overdue` (past due date, even if part paid) → `part_paid` → `sent`.
- **Why:** stored payment status goes stale the moment an allocation is reversed (invariant 5). An invoice that is
  part paid *and* late needs chasing, so `overdue` wins over `part_paid`.
- **Rejected:** a `status` column updated by triggers or by the allocation service — two sources of truth.

## D-06 — Backend is organised by feature (domain folders), not by layer
- **Decision:** `backend/app/<feature>/` holds that feature's `models.py`, `schemas.py`, `service.py`, `router.py`
  (e.g. `invoices/`, `allocations/`, `statements/`). Shared plumbing lives in `app/core/`. `app/db_models.py` imports
  every feature's models so Alembic and `scripts/erd.py` see all tables. Tests stay flat in `backend/tests/test_*.py`.
- **Why:** when working on one feature, everything it touches is in one folder; it is easy to show an examiner
  "this is the whole of allocation". Routers stay thin and call their own service; a feature may call another
  feature's service, never its router.
- **Rejected:** layered `app/models`, `app/services`, `app/api` (the starter's original layout) — one feature is
  spread over four folders.
- **Consequence:** invariant 4 now points to `backend/app/allocations/service.py::allocate()`.

## D-07 — Every tenant table has its own workspace_id
- **Decision:** `payment_allocations` and `audit_events` carry `workspace_id` even though it could be reached by a join.
- **Why:** invariant 8 is easiest to check when every query has a plain `WHERE workspace_id = :ws`. A missing filter
  is then visible in review, not hidden behind a join.
- **Rejected:** deriving the workspace via joins — fewer columns, harder to audit.

## D-08 — Design system: ui-ux-pro-max output, palette replaced
- **Decision:** visual direction is "Minimalism & Swiss Style" with IBM Plex Sans/Mono, as generated by the
  ui-ux-pro-max skill. The generated gold primary and purple accent were replaced with navy ink (`slate-900`) on white,
  plus a dark theme. See `design-system/reconcile/MASTER.md`.
- **Why:** gold is the same hue as the `part_paid` badge, so the brand would blur with status meaning; purple breaks
  the skill's own "no AI purple" anti-pattern. In Reconcile colour is reserved for meaning (status, errors).
- **Rejected:** the skill's dark OLED / Fira Code direction — striking, but dark-only and its green accent clashes with `paid`.

## D-09 — Plural table names, UUID primary keys
- **Decision:** tables are `workspaces`, `users`, `customers`, `invoices`, `transactions`, `payment_allocations`,
  `audit_events`. Primary keys are UUIDs.
- **Why:** `user` is a reserved word in PostgreSQL; plural names match CLAUDE.md. UUIDs don't leak how many invoices
  another workspace has and can be created before insert.
- **Rejected:** serial integer ids — guessable across tenants.

## D-10 — ERD lives as Mermaid in docs/ERD.md, checked by a script
- **Decision:** the ERD is hand-written Mermaid in `docs/ERD.md`. `backend/scripts/erd.py` prints Mermaid from
  `SQLModel.metadata`; we compare the two after model changes.
- **Why:** Mermaid is plain text, renders on GitHub and in VS Code, and diffs in git. The script proves the diagram
  matches the code without adding a dependency.
- **Rejected:** image-only diagrams (dbdiagram, draw.io) — they drift from the code silently.

## D-11 — Paystack external_reference is unique per source, not per workspace
- **Decision:** `UNIQUE (source, external_reference)` on transactions.
- **Why:** Paystack references are globally unique, and the webhook arrives before we trust which workspace it is for.
  A duplicate webhook hits this constraint and the whole DB transaction (insert + allocation) rolls back (invariant 3).
  Bank statement lines leave `external_reference` NULL, and NULLs never collide in a Postgres unique constraint.

## D-12 — Invoices have a number AND a separate payment reference
- **Decision:** `number` is sequential per workspace (`INV-0001`), for humans. `reference` is random (`RCN-7K4Q2M`, 6 characters
  from an alphabet without 0/O/1/I/L), and it is what the payer is asked to quote on the transfer.
- **Why:** exact-reference matching scans free-text bank narrations. "INV-0001" exists in every workspace and looks like
  other companies' invoice numbers, so it would cause false matches. A random code with a fixed prefix is distinctive,
  and leaving out lookalike characters reduces typos when customers copy it into a banking app.
- **Rejected:** using the invoice number as the reference — ambiguous in narrations.

## D-13 — "Today" is the date in Lagos
- **Decision:** overdue checks and default dates use `lagos_today()` (UTC+1, no daylight saving). Timestamps are stored in UTC.
- **Why:** between 00:00 and 01:00 in Lagos it is still the previous day in UTC; an invoice due "yesterday" would not
  yet show as overdue. A fixed +1 offset is exact for Nigeria and needs no timezone database on Windows.

## D-14 — Invoice numbers are allocated under a workspace row lock
- **Decision:** `_next_number()` runs `SELECT ... FROM workspaces WHERE id = :ws FOR UPDATE`, then counts the workspace's invoices.
- **Why:** two "create invoice" clicks at the same moment would otherwise both count N and both pick N+1; the unique
  constraint would then reject one with a confusing error. The lock makes them take turns and is released at commit.
  Invoices are never deleted (only voided), so count + 1 never reuses a number.
- **Rejected:** a Postgres sequence — one global sequence would leave gaps and not restart per workspace.

## D-15 — Status filters run after the status is derived
- **Decision:** `GET /api/v1/invoices?status=overdue` loads the workspace's invoices, derives each status in Python, then filters.
- **Why:** paid/part_paid/overdue are not columns (D-05), so they can't be a SQL WHERE without copying the rules into SQL.
  One definition of status is worth more than speed at SME volumes (hundreds to a few thousand invoices).
- **Revisit if:** a workspace has tens of thousands of invoices.

## D-16 — Audit rows are written in the same commit as the change
- **Decision:** `audit.service.record()` only adds the row to the session; the calling service commits once.
- **Why:** a change without its audit row (or an audit row for a change that rolled back) would make the trail lie (invariant 7).

## D-17 — allocate() locks the bank line first, then the invoice, and re-sums after locking
- **Decision:** `SELECT ... FOR UPDATE` on the transaction row, then on the invoice row, always in that order. Existing
  non-reversed allocations are summed only after both locks are held.
- **Why:** two accountants (or an accountant and a webhook) can allocate at the same instant. The lock makes the second
  request wait; READ COMMITTED means its sum then includes the first request's committed allocation, so it can't
  over-allocate. A fixed lock order prevents deadlocks (A holds the line and waits for the invoice while B holds the
  invoice and waits for the line). `tests/test_hard_part.py` races real threads, and fails if the locks are removed.
- **Rejected:** SERIALIZABLE isolation with retries — also correct, but harder to explain and every caller must retry.
  A CHECK constraint can't do it either: it can't see other rows.

## D-18 — allocate() and reverse() never commit
- **Decision:** they `flush()` (so constraint errors surface immediately) and return; the caller commits.
- **Why:** the Paystack webhook must insert the transaction and its allocation in one DB transaction (invariant 3).
  If allocate() committed by itself, a crash between the two would leave a payment recorded but not allocated, or the
  other way round.

## D-19 — SUM() results are cast back to BIGINT
- **Decision:** `CAST(COALESCE(SUM(amount_kobo), 0) AS BIGINT)` in `allocations.service`.
- **Why:** PostgreSQL returns SUM of a BIGINT as NUMERIC, which psycopg turns into a Python Decimal. Casting keeps every
  amount a plain int end to end (invariant 1).

## D-20 — Statement import: CSV only, credits only, all-or-nothing
- **Decision:** the import accepts CSV (UTF-8 or Excel's cp1252). Only credits (money in) are stored; debits are counted
  and reported as `debits_ignored`. If any row can't be parsed, the whole file is rejected with the line number, and
  nothing is inserted.
- **Why:** reconciliation matches money IN to invoices; storing debits adds rows nothing uses yet. Rejecting the whole
  file means a half-imported statement can never exist, so "re-import adds nothing" stays easy to reason about.
- **Revisit:** XLSX support once real bank exports (docs/research/) show which banks only offer Excel.

## D-21 — Duplicates are stopped by the database, not by checking first
- **Decision:** one `INSERT ... ON CONFLICT ON CONSTRAINT uq_transactions_workspace_fingerprint DO NOTHING RETURNING id`
  for the whole file. Lines returned were added; the rest were duplicates.
- **Why:** "SELECT to see if it exists, then INSERT" has a gap in which two imports of the same file can both insert.
  The unique constraint closes that gap, and it is one statement instead of one query per line.

## D-22 — Settlement lines are recognised by "PAYSTACK" in the narration
- **Decision:** a credit whose narration contains PAYSTACK (any case) is stored with `kind = settlement` (invariant 6).
- **Why:** these are Paystack paying out money whose individual customer payments the webhook already recorded;
  matching them to invoices would count that money twice.
- **Revisit:** check the exact settlement narration in real exports (docs/research/); if a bank abbreviates it, extend
  `is_settlement()` and add a fixture.

## D-23 — Rows with more cells than the header are rejected
- **Decision:** a data row with extra non-empty cells is an error, not truncated.
- **Why:** an unquoted `25,000.00` splits into `25` and `000.00`; silently reading ₦25 would lose ₦24,975.
  A test in `test_statement_parsers.py` covers it.

## D-24 — Parsers are built on synthetic fixtures until real exports arrive
- **Decision:** `bank_a` and `bank_b` are invented formats (`backend/tests/fixtures/statements/`, marked synthetic).
- **Why:** development could not wait for real statements. Each real bank becomes one small parser module listed
  in `parsers/detect.py`, plus a redacted fixture; nothing else changes. Real exports also belong in docs/research/
  as evidence for the research gate.

## D-25 — Matching score details
- **Decision:** amount equal to outstanding = 50. Name: rapidfuzz `token_set_ratio` on normalised names (upper case,
  "&" → AND, punctuation and LTD/LIMITED/PLC removed), best of customer name and aliases; below 85% → 0, otherwise
  `round(30 × similarity / 100)` (85% → 26, 100% → 30). Date: `round(20 × (14 − days) / 14)` for 0–13 days after the
  invoice was sent (Lagos date), else 0. Suggested when the top score ≥ 70 **and** it leads the runner-up by ≥ 10.
- **Why:** these are the CLAUDE.md weights made precise. The 10-point margin is "one clear top candidate": two
  identical invoices for the same customer both score 100, and guessing between them would be wrong half the time.
- **Rejected:** machine-learned weights — no training data, and impossible to explain line by line.

## D-26 — Reference matching ignores case, spaces AND punctuation
- **Decision:** both the invoice reference and the payment text are reduced to letters and digits before comparing
  (`"rcn - vyq esr"` → `RCNVYQESR`). Exactly one open invoice quoted + amount ≤ outstanding → auto-allocate the whole credit.
  More than one invoice quoted, or too much money → the queue.
- **Why:** customers type references by hand into banking apps; dashes and spaces get dropped or added. The `RCN` prefix
  and 6 random characters (D-12) keep accidental matches inside joined-up text very unlikely.

## D-27 — Auto-matching runs inside the statement import's transaction
- **Decision:** after inserting new credits, the import calls `reconciliation.auto_match()` for just those lines, then
  commits once. `POST /api/v1/reconciliation/auto-match` re-runs it over every unallocated credit.
- **Why:** an import either lands with its automatic allocations or not at all. The re-run covers money that arrived
  quoting a reference before its invoice was sent (drafts are never candidates). The system is the actor
  (`created_by` = null, method `auto`), so the audit trail shows a person didn't do it.

## D-28 — "Not this one" is stored as an audit event
- **Decision:** rejecting a candidate writes a `match.rejected` audit event with the transaction and invoice ids; the
  queue and auto-match skip those pairs.
- **Why:** the rejection must be audited anyway (invariant 7), and the event already holds both ids, so a separate
  table would store the same fact twice. Volumes are tiny (a few rejections per month per SME).
- **Revisit if:** rejections need to be undone; then a proper `match_rejections` table with a `revoked_at` is cleaner.

## D-29 — Match reasons contain no money amounts
- **Decision:** reasons say "Amount equals the amount outstanding", not "… ₦90,000.00".
- **Why:** invariant 1 says naira formatting happens only in the UI. The UI already shows both amounts next to the reasons.

## D-30 — The Paystack webhook trusts only verify-transaction
- **Decision:** after the signature check, the webhook takes only the `reference` from the body, calls Paystack's
  verify-transaction endpoint, and records the amount, status, currency and `metadata.invoice_id` that Paystack returns.
- **Why:** a valid signature proves Paystack sent the body once, not that it is fresh or that our secret never leaked.
  Asking Paystack again means a replayed or forged body can't change the amount we record.
- **Rejected:** recording straight from the webhook body — fewer calls, but one leaked secret becomes free money.

## D-31 — Paystack money that can't be allocated is still recorded
- **Decision:** if `allocate()` refuses (invoice void, or more than is outstanding), the Paystack credit is saved
  unallocated and appears in the exception queue. Nothing is split automatically.
- **Why:** the money really arrived; dropping it would hide it. Whether to refund, split, or move it to another
  invoice is the accountant's call. Payments for an unknown invoice id are not stored: without the invoice there is
  no workspace to store them in.

## D-32 — Answer 502 when Paystack can't be reached
- **Decision:** the webhook verifies synchronously. A network error, timeout or 5xx from Paystack returns 502.
- **Why:** any non-200 makes Paystack retry later, and retries are harmless because a duplicate pays once (invariant 3).
- **Rejected:** answering 200 at once and verifying in a background task — faster, but a failure there would be lost silently.

## D-33 — One Paystack secret per deployment
- **Decision:** `PAYSTACK_SECRET_KEY` is a single setting, used to check signatures and to call Paystack.
- **Why:** MVP scope. Per-workspace Paystack accounts would need the workspace before the signature can be checked,
  which changes the design (e.g. a per-workspace webhook URL).

## D-34 — Online payment needs the customer's email, and asks only for what is outstanding
- **Decision:** `POST /api/v1/public/invoices/{token}/pay` initialises Paystack for the invoice's current outstanding
  amount, with the customer's stored email and `metadata.invoice_id`. No email, or nothing owed (paid / void) → 409.
- **Why:** Paystack's initialise requires an email. Asking only for the outstanding amount means a card payment can't
  overpay unless a bank transfer lands between opening and finishing checkout; D-31 sends that rare case to the queue.
- **Rejected:** asking the payer to type an email on the public page — another form field and validation for a case
  the business can fix by adding the customer's email. Revisit if many customers have none.

## D-35 — Only 400/404 from verify-transaction means "ignore"; everything else means "retry"
- **Decision:** refines D-32. If Paystack answers 400 or 404 (it doesn't know the reference), the webhook returns
  200 `ignored`. Any other non-200 answer (429 rate limit, 401/403 bad key, 408, 5xx) returns 502.
- **Why:** a 200 makes Paystack stop retrying. A rate limit or rotated key says nothing about the payment, so
  answering 200 would lose a real card payment for good: it would surface only inside a settlement line, and those
  are never matched (invariant 6). Retries are harmless (invariant 3).

## D-36 — Feature routes are versioned under /api/v1
- **Decision:** every feature router is mounted under `/api/v1` in `app/main.py` (one constant, `API_V1_PREFIX`).
  Routers only declare their own path (`/invoices`, `/webhooks`). `GET /api/health` stays unversioned.
- **Why:** the Paystack webhook URL and the public invoice link are given to outside parties and can't be changed
  for them overnight. If a response shape ever has to break, a `/api/v2` router can run beside v1 while old callers
  move over. Adding the prefix now, before any frontend screen calls the API, costs nothing.
- **Health stays unversioned:** it is a probe for docker compose and Render, not part of the API contract.
- **Rejected:** version in a header (`Accept: application/vnd.reconcile.v1+json`) — invisible in logs and in the
  browser, and Paystack can't send custom headers to a webhook. No version at all — fine while the frontend is the
  only client, but changing the webhook URL later means a Paystack dashboard change during live payments.
